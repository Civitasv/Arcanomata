# F02/F03 acceptance and playable combinations

## Observable rule causality (F02)
- Select an orb to see the actor ID, last matched condition, target ID and the last six actions.
- Each action records rule index, target category/ID, time, channel, cross-species consumption and energy delta. A bounded global ring records the latest 90 events.
- The HUD shows renderer+simulation milliseconds (smoothed), peaks for living spells/enemies/marks, damage taken, transferred energy and cross-species reactions.
- Idle agents are gently drawn back toward the player so spells do not permanently drift away from the action. Hunters now pulse when they can sense an enemy and an enemy is inside pulse radius.
- Automatic seeded model tests cover combat, high-load limits and deterministic evolution; browser CI smoke covers dynamic editors, movement, pause/retry, agent inspector, upgrades, and desktop/narrow viewports.

## Cross-species grammar (F03)
Each rule is:
\`\`\`json
{ "when": "mark", "do": "seek", "channel": "beacon", "scope": "other" }
\`\`\`
- Channels: \`beacon\` (guidance), \`danger\` (warning), \`supply\` (energy gathering).
- Scope: \`other\`, \`self\`, \`any\`; applies to mark/ally sensing.
- \`mark\` writes to the chosen channel, tagged with creator species and TTL.
- \`mark\` reads only the selected channel and source scope.
- \`ally → share\` transfers up to six energy at a time. Donor loses exactly the amount recipient gains, and must keep a reserve.
- \`tick → seek\` and \`enemy → share\` are incompatible and rejected by the interpreter; browser editor also steers selections to valid pairs.

## Three reproducible recipes made from generic primitives
1. **Beacon hunting**: Scout \`enemy → mark(beacon)\`; hunter \`mark(beacon, other) → seek\` and \`enemy → pulse\`. The hunter learns a target location without a direct instruction from the scout.
2. **Warning ring**: Scout \`enemy → mark(danger)\`; hunter \`mark(danger, other) → flee\` plus \`enemy → pulse\`. Hunters move away from dense threat zones while still emitting damaging pulses.
3. **Supply relay**: Hunter \`tick → mark(supply)\`; scout \`mark(supply, other) → seek\` and \`ally(other) → share\`. A scout tracks another spell through a signal and can top up that other agent's energy without a hardcoded spell recipe.

Outcomes depend on position, timing, energy and enemies; a recipe describes rule intentions, not guaranteed emergent formations.

## Seeded replay protocol
The downloadable JSON contains:
- v1 header and integer seed;
- initial sanitized programs;
- per-fixed-tick normalized player input;
- ordered rule-edit and upgrade events indexed by tick.

\`replayRun(tape)\` validates size, event order and rule schema, rebuilds the world and executes all inputs at exactly 30 Hz. Export performs an exact model-state equality check before downloading. Import reconstructs the recorded **final state**, not animated playback.

## Three-minute deterministic performance benchmark (F02)

Run `npm run benchmark` to record the exact JSON report at `artifacts/three-minute-benchmark.json`. Three fixed seeds each execute:

- **Normal gameplay**: deterministic spiral input, real HP, upgrade selection, terminal state may be a loss before 180 seconds.
- **Immortal soak**: identical AI and enemy waves but player HP restored before each tick to force the full 180-second simulation and assess entity growth/CPU stress independently of survival skill.

Both report kills, damage, surviving agents, cross-species signals, pulse count, energy shared, peak agents/enemies/marks, CPU per-tick p50/p95/p99, and wall-clock time. The benchmark verifies entity caps and full-duration soak completion; exact CPU timings are machine-dependent. This is **not a browser FPS benchmark** or evidence of balanced human-play difficulty.
